# 라이브 카드뉴스 생성·검수 로직 (실제 MVP 기준)

**목적** — 실제 앱이 카드뉴스를 **어떻게 생성·검수하는지**와 **프롬프트가 어디 있는지**를 정리한다.
생성 로직·프롬프트(⭐)와 검수 로직·프롬프트(⭐)를 이어받아 **고도화**할 사람을 위한 지도다.
"지금 어떻게 도는지 → 프롬프트 위치 → 고도화하려면 어디를 건드리나" 순으로 읽으면 된다.

작성 기준: `lib/workspace/ai.ts`, `lib/workspace/ai-review.ts`, `lib/workspace/verdict.ts`, `lib/workspace/compliance.ts`, `lib/llm/card-review.ts`

---

## 0. 먼저 — 라이브 vs 벤치 (헷갈리지 말 것)

카드뉴스 생성 코드가 두 갈래다. **고도화 대상은 라이브(`lib/workspace`)다.**

| | 라이브 (이 문서) | 벤치/실험 |
|---|---|---|
| 위치 | `lib/workspace/ai.ts` 등 | `lib/generate/*` |
| 누가 씀 | **실제 앱**(`app/api/cards`, `app/api/strategy`) | CLI·실험 스크립트(`npm run gen` 등) |
| 고도화 | ✅ 여기를 건드림 | 건드리지 않음 |

> `lib/generate`(벤치)는 옛 파이프라인이라 실제 화면과 무관하다. 생성·검수를 바꾸려면 반드시 `lib/workspace`를 본다.

## 1. 큰 그림 — 생성에서 발행까지

```
시작설문(SurveyProfile)
   │
   ▼
[P2 전략]  generateStrategy      → 이번 주 발행 주제 N개 제안
   │        (app/api/strategy)
   ▼  주제 선택
[P4 기획]  generatePlanOutline   → 페이지별 뼈대(아웃라인)
   │        (app/api/cards)
   ▼
[P5 제작]  generateCard          → 본문·캡션·해시태그·CTA 완성
   │        (app/api/cards, .../generate)
   ▼
[검수]    정규식 + AI 7축 → 4단계 판정(🟢🟡🔴⚫)
   │        (app/api/cards/[id]/review)
   ▼
[발행]    publishCard → 인스타 게시
            (app/api/cards/[id]/publish, /api/schedule)
```

| 단계 | 함수 | 파일 | API 라우트 | 프롬프트 위치 |
|---|---|---|---|---|
| P2 전략 | `generateStrategy` | `lib/workspace/ai.ts` | `app/api/strategy` | `strategySystemPrompt` (ai.ts) |
| P4 기획 | `generatePlanOutline` | `lib/workspace/ai.ts` | `app/api/cards` | 함수 내 인라인 system |
| P5 제작 | `generateCard` | `lib/workspace/ai.ts` | `app/api/cards`, `.../[id]/generate` | `cardSystemPrompt` (ai.ts) |
| 검수(AI) | `aiReviewFlags`→`reviewCard` | `ai-review.ts`, `lib/llm/card-review.ts` | `app/api/cards/[id]/review` | `card-review.ts` `userPrompt`/`systemPrompt` |
| 검수(정규식) | `runReview` | `lib/workspace/compliance.ts` | 여러 라우트 | `DOMAIN_RULES` (정규식) |
| 판정 | `decideVerdict` | `lib/workspace/verdict.ts` | (검수 결과에 적용) | — (순수 규칙) |

## 2. 생성 로직 상세

세 단계 모두 공통 구조: **API 키 있으면 Claude 호출 → 실패 시 처리, 키 없으면 템플릿(mock)**.
- `hasApiKey()`가 false면 `template*` 함수로 대체(의도된 mock, 키 없이도 앱이 돎).
- 키가 있는데 호출이 실패하면 **조용히 mock으로 덮지 않고 에러를 던짐** → 라우트가 503. (실제 장애를 숨기지 않으려는 설계)
- 공통 호출부: `callClaude(system, user, maxTokens)` — 일시 오류(429·5xx·네트워크)만 백오프 재시도, JSON만 추출(`extractJson`).

### 2-1. P2 전략 — `generateStrategy(survey, followers)`
- **하는 일**: 팔로워로 운영단계 진단(`diagnoseStage`: 세팅/누적/반응탐색/성장실험/수익화준비) → 그 주에 올릴 **주제 N개**(`recommendedCount` = 주간 업로드 역량, 2~7) 제안.
- **출력**: `{diagnosis, weeklyGoal, focus[3], topics[N]}` (각 topic: title·goal·hookDirection·why).
- **프롬프트 요지** (`strategySystemPrompt`): 컨셉 그라운딩(니치·브랜드키워드·문체) / 운영단계별 목표(초기엔 저장·팔로우·공유) / 뻔한 템플릿 금지 / **지어낸 통계 금지** / 민감도메인 완화 표현.
- mock: `templateStrategy` (단계별 고정 카피).

### 2-2. P4 기획 — `generatePlanOutline(survey, input)`
- **하는 일**: 본문 전체가 아니라 **페이지별 뼈대(headline + 한 줄 body)** 만. 가벼움(max_tokens 1500).
- **프롬프트 요지** (함수 내 인라인): 서사 흐름(후킹→문제→관점전환→예시→핵심→적용→CTA) / 페이지 수에 맞춰 압축 / **★추천·리스트형 주제는 서사 강요 말고 "각 장 = 추천 항목 하나씩"** / 중간 슬라이드는 실질 정보로.
- mock: `templatePlan`.

### 2-3. P5 제작 — `generateCard(survey, input, outline)`
- **하는 일**: 아웃라인을 받아 **본문·캡션·해시태그·CTA 완성**.
- **프롬프트**: `cardSystemPrompt(survey, format)` — **`export`돼 있어** 프롬프트 비교 스크립트도 "라이브와 동일한" 프롬프트를 씀. 구성:
  - `common`: 브랜드키워드·문체·금지표현·캡션길이·해시태그스타일·민감도메인
  - `qualityRules`: **[빈 카피 금지]** / **[정보 밀도]** 실제 동작·단계·항목으로 채움 / **[추천은 실물을 이름으로]** / **[지어내지 말 것 — 검증형 하드팩트만]**(통계·가격·영업시간 등만 금지, 나머지 질적 정보는 풍부하게)
  - 포맷 분기: **릴스**(대본) vs **카드뉴스/사진첨부형**(카피)
- mock: `templateCard`.

> 💡 **핵심 설계**: 생성 프롬프트는 "지어내면 안 되는 건 **검증형 하드팩트(수치·가격 등)뿐**, 나머지 내용은 풍부하게"라는 기조다. 즉 **생성에서 과하게 막지 않는다** — 이게 아래 검수 철학과 짝을 이룬다.

## 3. 검수 로직 상세 — 3계층

검수는 **정규식(규칙) + AI(의미) → 4단계 판정**으로 합쳐진다.

### 3-1. 정규식 컴플라이언스 — `compliance.ts` `runReview`
- 민감 도메인별 **정규식 룰셋**(`DOMAIN_RULES`): `hard`(명백 위법 → 차단) / `soft`(회색지대 → 경고).
  - 예) 금융: `hard=/원금\s*보장/` 등(자본시장법), `soft=/무조건\s*오른다/` 등.
- 빠르고 결정적. AI 없이도 도는 1차 방어선.

### 3-2. AI 의미 검수 — `ai-review.ts` `aiReviewFlags` → `lib/llm/card-review.ts` `reviewCard`
- 카드 내용을 Claude로 **7축 채점**: `factuality`·`regulatory`·`tone`·`request`·`completeness`·`format`·`ux`.
- **프롬프트**(`card-review.ts` `userPrompt`)의 핵심 = **규제 판단 원칙**:
  - `pass`: 주관적 의견·추천("무조건 가야 돼요", "강추") — **열정·과장 자체는 안 막음**
  - `warn`: 근거 없는 객관적 우위·수치("1위", 출처 없는 통계) — 회색지대
  - `fail`: ①인스타가 실제 삭제하는 해악 ②한국 법령 위반(표시광고법·의료법·자본시장법)에 **명백할 때만**
  - **애매하면 pass/warn (Precision 우선 — 오경고가 신뢰를 깎으므로)**
- 결과(7축)를 `toFlag`가 워크스페이스 `ReviewFlag`로 매핑. **⚫차단은 `regulatory+block`(법령)에만** 한정 — AI 오판이 발행을 하드블록하지 않게. 사실 오류(factuality+block)도 최대 🔴.
- 키 없음/실패 시 `available:false` → 빈 배열 → **정규식 검수만으로 흐름 유지**(안 깨짐).

### 3-3. 4단계 판정 — `verdict.ts` `decideVerdict`
| 판정 | 조건 | 발행 |
|---|---|---|
| ⚫ 차단 | 필수축(규제) `level=fail` = 명백 위법 | 불가 |
| 🔴 경고 | 필수축 `level=warn` = 회색지대 | 책임 동의 후 발행 |
| 🟡 검토 | 그 외 감지(품질·톤 등) | 그대로 발행 자유 |
| 🟢 통과 | 감지 없음 | 바로 발행 |
- `verdictGate(verdict, consent)`: ⚫은 무조건 막고, 🔴은 "책임 동의" 체크 필요.

> 💡 **당신(팀장)이 말한 ⭐3 통찰이 코드에 그대로 있어요**: "생성에서 규칙으로 막으면 품질이 떨어진다 → 생성은 느슨하게, 검수에서 확실히." 실제로 **생성 프롬프트는 하드팩트만 금지(느슨)**, **검수는 Precision 우선 + 차단은 법령만**. 그래서 고도화 시 "검수를 어떻게 더 정확히(오경고 없이) 잡느냐"가 핵심 레버다.

## 4. mock ↔ 실 LLM 전환

- 스위치: `ANTHROPIC_API_KEY` 존재 여부(`hasApiKey`/`aiAvailable`). 모델은 `ANTHROPIC_MODEL`(기본 `claude-opus-4-8`).
- 키 없음 = 템플릿(mock)으로 전 과정 동작(개발·데모). 키 있음 = 실제 Claude 생성/검수.
- 생성 파이프라인(벤치) 쪽은 별도로 `LLM_PROVIDER`(mock|anthropic)도 있음(.env.example 참고).

## 5. 고도화하려면 어디를 건드리나 (⭐2·3 핵심)

| 하고 싶은 것 | 건드릴 곳 |
|---|---|
| **전략(주제 제안) 품질** | `ai.ts` `strategySystemPrompt` |
| **기획(구성/뼈대) 품질** | `ai.ts` `generatePlanOutline` 내 system 프롬프트 |
| **제작(본문 카피) 품질** | `ai.ts` `cardSystemPrompt` (`common`·`qualityRules`·포맷 분기) |
| **AI 검수 기준·강도** | `lib/llm/card-review.ts` `userPrompt`(규제 원칙·7축) / `systemPrompt` |
| **검수 판정 강도**(어느 축이 차단/경고/검토) | `ai-review.ts` `toFlag` 매핑 + `verdict.ts` `decideVerdict` |
| **정규식 도메인 룰** | `compliance.ts` `DOMAIN_RULES` |
| **mock 결과물**(키 없이 보이는 것) | `ai.ts` `template*` 함수들 |

> ⚠️ `lib/deck-schema.ts`·`concept-schema.ts`(공유 계약)나 출력 JSON 스키마를 바꾸면 렌더·DB·프론트가 함께 깨질 수 있음 — 스키마 변경은 팀 공유 후.

## 6. 고도화 후 검증하는 법

라이브 함수를 실제로 태워 확인하는 스크립트가 있다(자세한 건 `scripts/README.md`):

```bash
npm run verify:strategy   # P2 전략 프롬프트 검증
npm run verify:chain      # P2→P4→P5 전체 체인
npm run verify:review     # AI 검수 배선
npm run persona-stress    # 6개 계정 컨셉 × 실제 체인 (환각/톤/가드레일)
npm run reco-test         # 추천 콘텐츠 프롬프트(환각 회피) 실험
```

> 다양한 카테고리(의료·금융·노래추천·맛집·홈트 등)로 꼭 테스트할 것 — 프롬프트 변경은 한 분야에서 좋아도 다른 분야에서 나빠질 수 있다.
